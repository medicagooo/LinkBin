# 06: Large files — stream to storage within the invocation's budget

**What to build:** A file at the per-file limit is collected without exhausting memory and without
overshooting the time a single invocation is allowed, using the faster path measured in 04. If 04
showed that no single invocation can carry a file that size, this ticket implements the fallback
instead: the file is collected across several invocations with its progress recorded so the next one
continues.

**Blocked by:** 05.

**Status:** 4 of 10 met and tested offline. The six that are not are one gap seen from several directions: **an upload interrupted between invocations cannot be continued**, because although `multipart_sessions` exists with exactly the right columns, NOTHING writes to it — `storeStream` returns an `uploadId` and no caller records it. That is waste rather than corruption, since a later run starts the file again, and it is the honest boundary of what one invocation can promise. Two smaller unknowns: which READ path is viable is ticket 04's question rather than this one's, and the multipart abort is unverifiable locally because the simulator keeps incomplete uploads invisible.

- [ ] The store handles a file at its declared limit, one byte over, and a multi-part upload with a hash that matches the bytes read back — all asserted in `store.test.ts` against simulated storage. **A 100 MB file against a REAL machine is not tested**, because that needs a host.
- [x] Peak memory stays near one part rather than near the file size: batches are copies of exactly `partSize` and the released chunk is freed as it is sent, with a test asserting peak usage against the part size rather than the file size. The one case that is NOT bounded is inherent and stated in `store.ts`: a chunk larger than the part size must be buffered whole before it can be split, so peak memory is the largest single chunk the source hands over. With a declared size that is avoidable and the code avoids it.
- [ ] Reading uses the serial path, which is the fallback the criterion names. **Which path 04 measured as viable is unknown because 04 has not run** — it needs a machine. The windowed session-channel path is not implemented, and choosing between them is exactly what 04 exists to decide.
- [x] A file above the per-file limit is recorded as skipped, with its size, and **its bytes are never requested** — asserted by counting calls to `remote.read` and requiring zero, rather than by checking the outcome, because a test that only checked the outcome would pass even if the transfer had happened first. The gate is asked from the `stat` alone, so nothing is opened. Capacity is refused at the same point, with the distinction kept: a size skip is a decision about the limit, a capacity refusal needs acting on.
- [ ] Uploads above the chunking threshold are sent in parts, with the parts held as R2 multipart parts rather than in memory — so the state lives in storage, outside the Worker, which is what makes a file larger than the isolate storable at all. **NOT DONE, and worth stating precisely:** `multipart_sessions` exists in the schema with exactly the right columns and NOTHING writes to it. `storeStream` returns an `uploadId`, so the id is available, but nothing records it — which means an upload interrupted between invocations leaves parts nothing references, and a later run starts the file again rather than continuing it. That is waste rather than corruption, and the cleanup criterion below is the other half of the same gap.
- [x] All parts except the last are the same size, as storage requires. Enforced by issuing batches at exactly `partSize`, and covered by its own tests plus the adversarial audit that found the original version uploaded a source chunk larger than the part size as one oversized part — which storage refuses only AT COMPLETION, after the whole transfer.
- [ ] An abandoned upload is aborted on every failure path, and `store.test.ts` asserts nothing is retrievable afterwards. **The abort itself is unverified**, and `store.ts` says so: the local storage simulator keeps incomplete multipart uploads invisible, so cleaning one up and leaving it behind look identical. Confirming it needs a real bucket.
- [ ] A transfer that exceeds the run's remaining time is stopped at a recorded point rather than being killed mid-write. The deadline is checked before each read and the failing path reports `committedBytes: 0`, because the abort discarded every uploaded part — so a caller is never told to resume from bytes that no longer exist. What is NOT shown is a real invocation being killed and leaving a resumable state: that needs the deployed Worker and a large real file.
- [ ] If the budget is exceeded the file is left in a state that does NOT look complete: the multipart upload is aborted, so nothing is readable under the key, and the run closes as `stopped` with a cursor rather than `finished`. A resumed upload in the sense of continuing an R2 multipart upload is NOT implemented — see the `multipart_sessions` note above.
- [x] Tests cover four of the five: at the limit, one byte over, a multi-part upload, and an interrupted transfer. **A RESUMED upload is the one missing**, and it is missing because resumption is not implemented — see `multipart_sessions` above. Writing a test for it would mean writing the feature.
