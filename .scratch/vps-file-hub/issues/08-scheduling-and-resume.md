# 08: Scheduling — unattended runs that resume where they stopped

**What to build:** Collection happens on its own. One run covers one machine's incremental scan under
a wall-clock budget; if it does not finish, the next run continues from where it stopped instead of
starting over; and one machine being unreachable does not stop the others.

Resumability is a premise rather than error handling: the scheduler is weakly delivered and a
scheduled minute may simply be skipped, and 50 machines cannot be scanned within one invocation, so
"did not finish" has to be a normal state that the system can pick up from.

**Blocked by:** 05, 07.

**Status:** 9 of 11 met and tested offline. The two that are not are the same two things. **Nothing runs on a schedule**: no 	riggers.cron is declared, so collection happens only when someone asks — and adding the trigger would begin unattended runs against real machines, which is the operator's decision rather than a step to take while they are not looking. **And the cursor records HOW MANY files were reached rather than a per-rule position**, so a resumed run does not yet skip completed work. The rotation, the unreachable-machine handling, the wall-clock budget, the cursor's contents and the freshness report are all built and asserted.

- [ ] Collection runs ON DEMAND from the interface, and the route accepts either a session or the scheduler credential. **The SCHEDULE half is not done**: no `triggers.cron` is declared in `wrangler.jsonc`, so nothing calls the route on a timer and no invocation happens without a human. Adding the trigger is a configuration change I have deliberately not made, because it would begin running collections against real machines unattended — that is the operator's decision rather than a step to take while they are not looking. It is one block in `wrangler.jsonc` once a host is verified.
- [x] One run covers one machine's incremental scan, not all machines at once: `planRun` chooses a single machine, the run row names it, and the response reports `machineId`. Nothing in the route iterates machines.
- [x] A run respects a wall-clock budget comfortably below the platform's per-invocation ceiling, and leaves before it is killed: `DEFAULT_RUN_BUDGET_MS` is five minutes against a ceiling far above it, the deadline is checked before each read, and a walk that reaches it stops and reports `stoppedEarly`. The run is then closed as `stopped` rather than `finished`, which is what makes the distinction worth having. **The five minutes is a conservative default rather than a measured figure** — the ticket asks for it to be set from 04's measurement, which has not run.
- [x] A run that stops early records a cursor naming the machine and how far it reached: `closeRun(..., 'stopped', totals, cursorFor(hostId, outcomes))`, with a test asserting the stored `cursor_json` parses to `{ hostId, reached }` and that the state is `stopped` rather than `finished`. The position is a FILE COUNT rather than a resumable offset into one file — resuming an individual part-uploaded file is the separate gap recorded in ticket 06.
- [ ] The next run RESUMES FROM the cursor in the sense that it reads it, reports it as `resumeFrom`, and `planRun` decides whether it belongs to the chosen machine — with the ignored case said out loud rather than left looking like the cursor was never written. **It does NOT skip work already completed**: the cursor records how many files were reached and the walk starts from the beginning of the rule set regardless. Making it skip means a per-rule position, which is the same shape as the resumption gap in ticket 06.
- [x] A run that skipped a scheduled minute simply runs later: nothing counts minutes or expects a run per interval. The rotation is driven by when each machine was last ATTEMPTED, so a missed trigger only means the next invocation finds the same machine still the longest-waiting one. No state assumes an interval elapsed.
- [x] A machine that is unreachable is recorded as unreachable and the run moves on: the connection failure writes an `unreachable` issue naming the machine with the reason in the machine's own words, and answers 200 with `connected: false` rather than throwing — so the failure is a receipt rather than an obstruction, and the rotation picks the next machine on the next invocation. Asserted through the HTTP edge.
- [x] Machines are rotated so that one slow machine cannot permanently starve the others: ordered by when each was last ATTEMPTED rather than last succeeded, so a machine that keeps failing cannot be skipped forever while a healthy one is always chosen. Ties break on id, so two invocations cannot disagree. Covered by `schedule.test.ts` and by the rotation test in `collect.test.ts`.
- [x] The interface shows when each machine was last collected successfully: `GET /api/freshness` reports the seconds since each one last FINISHED a run, and the panel renders it per machine. A machine that has never succeeded says so in words rather than showing a duration, because zero would read as "just now" — the opposite of the truth.
- [x] The freshness achieved in practice is reported, and against a stated target rather than as a bare number: `FRESHNESS_TARGET_MS` is 40 minutes — the middle of the spec's "a few tens of minutes" — and travels with the report as `targetSeconds`, so "worst is 3000 seconds" can be judged rather than guessed at. The WORST case is reported rather than an average, because an average hides the machine that is never collected. **What is not reported is the figure over TIME**: this is the current staleness, so a machine consistently 39 minutes behind and one that oscillates read the same.
- [x] Tests cover a budget-exhausted run resuming (the cursor is recorded, the run is `stopped`, and `planRun` resumes from a cursor belonging to the chosen machine), a skipped trigger, an unreachable machine among reachable ones, and rotation across machines — the last three in `schedule.test.ts` and `collect.test.ts`, the first through the edge. **What is NOT covered is a resumed run doing less work than a fresh one**, because the position is a count rather than a per-file offset; that is the same gap as above.
